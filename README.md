# SRK Case Manager

A bilingual (Bengali/English) case-management and legal-document drafting application built with React, TypeScript, Vite, Electron and Capacitor.

## Project platforms

- **Windows:** Electron desktop application packaged as an NSIS installer.
- **Android:** Capacitor Android application packaged as a debug APK by GitHub Actions.
- **Data:** The existing application data layer and legal workflows are retained. Do not treat a successful APK/EXE build as proof that cloud AI or cross-device synchronisation is configured.

## Requirements

- Node.js 22
- npm
- For Android local builds: Java 21, Android SDK and Gradle (the GitHub Actions workflow provisions these)
- For Windows local installer builds: Windows and the Electron Builder toolchain

## Run the development application

```bash
npm install --legacy-peer-deps
npm run dev
```

The development server is started through `tsx server.ts`.

## Build for Windows

```bash
npm install --legacy-peer-deps
npm run dist:win
```

The installer is written to `release/`.

## Build for Android

```bash
npm install --legacy-peer-deps
npm run build
npx cap add android
npx cap sync android
```

If the `android/` platform directory already exists, skip `npx cap add android`. Then build:

```bash
cd android
./gradlew assembleDebug
```

On Windows use `gradlew.bat assembleDebug`.

## GitHub Actions builds

The workflows under `.github/workflows/` build the Android APK and Windows installer on pushes and pull requests targeting `main`, and can also be started manually from the Actions tab.

Download the generated files from the completed workflow run's **Artifacts** section. The Android workflow currently creates a **debug APK**; it is not a Play Store release-signed APK.

## AI and connectivity status

The AI drafting routes are implemented in `server.ts` and the web interface calls `/api/ai/...`. The server uses the server-side `GEMINI_API_KEY` environment variable for Gemini requests.

**Important:** the current Electron and Capacitor packaging contains the web application, not a separately deployed Express API service. Therefore, do not assume that AI API calls will work in an installed EXE/APK merely because the app builds. A secure runtime/backend connection must be configured before enabling cloud AI in production. Never place a Gemini API key in frontend code, `VITE_*` variables, or a committed file.

The intended architecture is offline-first:
1. Local case records and core workflows remain usable without internet.
2. Local AI can be selected when a compatible local model service is installed and configured.
3. Cloud AI / remote backup can be enabled through a separately hosted HTTPS backend, with credentials kept server-side.

These three modes require runtime integration and device testing; this README does not claim that all three are already operational.

## Google Drive sync status

Google Drive is the selected cloud provider for the planned cross-device sync. The app must remain offline-first; the Drive folder is selected through Google authorization and the official Picker, not by typing a fake local filesystem path. Live two-way sync, conflict handling, secure token storage and sync notifications are not yet implemented. They require Google Cloud API/OAuth configuration and platform-specific testing. See the integration architecture document for the exact prerequisites. Do not treat a local backup path or a successful build as proof that Google Drive sync is connected.

## Environment variables

Copy `.env.example` to `.env.local` for local server development and set:

```env
GEMINI_API_KEY=your_server_side_key
```

Do not commit `.env.local` or any real API key.

## Repository structure

- `src/` — React application, UI components and application state
- `server.ts` — Express development/API server and AI routes
- `main.cjs`, `preload.cjs` — Electron main process and safe renderer bridge
- `android/` — Capacitor-generated Android platform (may be generated by CI)
- `.github/workflows/` — Android and Windows build pipelines

## Safety and release notes

- The CI Android artifact is a debug build. Create a separate release-signing process using GitHub Actions secrets before publishing.
- Do not commit production signing keystores, passwords, API keys or private certificates.
- Test upgrades against a backup before distributing an installer or APK to users.


## MSG91 WhatsApp and SMS integration status

MSG91 has been selected for client-facing WhatsApp and SMS. A server-only transport adapter has been added in `messaging/msg91.ts` using MSG91's documented SMS Flow and WhatsApp template APIs. Configure `MSG91_AUTH_KEY`, `MSG91_SMS_TEMPLATE_ID` and `MSG91_WHATSAPP_INTEGRATED_NUMBER` only in the trusted backend environment; never put them in frontend variables, the APK, the EXE or GitHub source.

**This is not yet an active messaging feature.** The application still needs a secure authenticated backend, consent capture/opt-out UI, a durable reminder queue/scheduler, approved Bengali/English templates, delivery-webhook verification and device-level testing. The transport module is not exposed as a public API route because the current app does not yet have server-side user authentication. Do not attempt live sends until those controls and MSG91 account/DLT/WhatsApp onboarding are complete.

Official API references: [MSG91 SMS Flow API](https://docs.msg91.com/sms/send-sms) · [MSG91 WhatsApp template API](https://docs.msg91.com/en/whatsapp/template-bulk).
